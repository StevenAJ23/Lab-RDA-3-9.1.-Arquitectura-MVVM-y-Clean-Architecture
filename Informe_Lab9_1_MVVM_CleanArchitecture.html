1. Introducción

El desarrollo profesional de aplicaciones Android ha evolucionado significativamente desde los enfoques monolíticos donde toda la lógica residía en una única Activity. Este antipatrón, conocido como "God Activity", genera problemas críticos como fragilidad ante cambios, imposibilidad de realizar pruebas unitarias aisladas y fugas de memoria (Memory Leaks) al rotar la pantalla del dispositivo.

El presente informe documenta la implementación del Laboratorio 9.1, cuyo objetivo central es construir una mini-aplicación de Gestión de Tareas Académicas aplicando estrictamente las directrices de Clean Architecture (Arquitectura Limpia) combinadas con el patrón de diseño MVVM (Model-View-ViewModel) y el paradigma Flujo Unidireccional de Datos (UDF). La solución emplea Jetpack Compose para la capa de presentación declarativa, junto con StateFlow y Flow de Kotlin Coroutines para la gestión reactiva del estado.

La aplicación prescinde de persistencia en base de datos real (Room) y utiliza un repositorio simulado en memoria que emite flujos reactivos, permitiendo concentrar el aprendizaje en la separación de responsabilidades y el desacoplamiento de capas.

2. Objetivos

2.1 Objetivo General

Implementar una aplicación Android funcional de gestión de tareas académicas aplicando los principios de Clean Architecture y el patrón MVVM con Flujo Unidireccional de Datos, garantizando la separación física de capas y la inmunidad de la interfaz ante cambios en el ciclo de vida.

2.2 Objetivos Específicos

  • Diseñar e implementar físicamente la separación de capas Domain, Data y Presentation como paquetes independientes dentro del proyecto Android.
  • Configurar un ecosistema reactivo donde el estado fluya hacia abajo mediante StateFlow y los eventos viajen hacia arriba mediante callbacks controlados (UDF).
  • Abstraer las operaciones de negocio mediante Use Cases, asegurando que sean independientes del framework de Android y de librerías externas de interfaz visual.
  • Implementar el Desafío Extra: una regla de dominio que prohíba títulos de tareas con menos de 5 caracteres, con recuperación controlada desde la UI sin crashes.

3. Marco Teórico

3.1 Clean Architecture

Propuesta por Robert C. Martin (Uncle Bob), la Arquitectura Limpia organiza el código en capas concéntricas donde las dependencias apuntan siempre hacia el núcleo (regla de dependencia). Cada capa solo conoce a las capas internas y nunca a las externas.

┌──────────────────────────────────┐
│ Frameworks & Drivers (UI, DB) │ ← capa más externa
│ ┌────────────────────────────┐ │
│ │ Interface Adapters (MVVM) │ │
│ │ ┌──────────────────────┐ │ │
│ │ │ Application (Use Cases)│ │ │
│ │ │ ┌────────────────┐ │ │ │
│ │ │ │ Domain/Entities│ │ │ │ ← núcleo puro
│ │ │ └────────────────┘ │ │ │
│ │ └──────────────────────┘ │ │
│ └────────────────────────────┘ │
└──────────────────────────────────┘

3.2 Patrón MVVM (Model-View-ViewModel)

MVVM separa la interfaz de usuario de la lógica de negocio mediante un ViewModel que actúa como mediador. El modelo expone el estado mediante flujos observables, la vista reacciona a esos flujos y envía eventos de usuario al ViewModel sin conocer la fuente de datos.

  • Model: entidades del dominio y repositorios de datos.
  • View: composables de Jetpack Compose que reaccionan al estado.
  • ViewModel: encapsula la mutabilidad, sobrevive cambios de configuración (rotación de pantalla) y coordina los Use Cases.

3.3 Flujo Unidireccional de Datos (UDF)

En UDF el estado fluye siempre en una sola dirección: el ViewModel expone un StateFlow inmutable que la vista consume mediante collectAsState(). Los eventos de usuario (clic en checkbox, guardar tarea) viajan en dirección contraria como llamadas a funciones del ViewModel, que actualiza el estado interno y el flujo se propaga automáticamente a la vista. 

Vista (evento usuario)  →  ViewModel.onXxx()  →  Use Case  →  Repository
Repository  →  Flow  →  Use Case  →  ViewModel._uiState  →  Vista (recomposición)

3.4 StateFlow y Flow de Kotlin Coroutines

  • Flow<T>: flujo frío y asíncrono. El repositorio emite listas de tareas cada vez que cambia el MutableStateFlow interno.
  • StateFlow<T>: flujo caliente con un valor actual siempre disponible. El ViewModel expone el UiState como StateFlow de solo lectura.
  • collectAsState(): suscribe un composable de Compose al flujo y dispara recomposiciones automáticas cuando el estado cambia.

4.2 Capa de Dominio (Domain Layer)

La capa de dominio es el núcleo de la arquitectura. No contiene ninguna dependencia de Android ni de librerías de interfaz visual, lo que garantiza su portabilidad y testabilidad completa.

4.2.1 Entidad AcademicTask

Modelo de datos inmutable que representa una tarea académica. Al ser una data class de Kotlin, provee automáticamente equals(), hashCode() y copy(), necesario para la mutación inmutable del estado. 

data class AcademicTask(
    val id: String,
    val title: String,
    val isCompleted: Boolean
)

4.2.2 Contrato AcademicTaskRepository

Interfaz que define las capacidades puras del sistema de forma abstracta. La capa de dominio solo conoce este contrato, nunca la implementación concreta, aplicando el principio de Inversión de Dependencias (DIP) de SOLID. 

interface AcademicTaskRepository {
    fun getTasksStream(): Flow<List<AcademicTask>>
    suspend fun addTask(title: String)
    suspend fun toggleTaskCompletion(taskId: String)
}

4.2.3 Caso de Uso GetTasksUseCase

Encapsula la única intención de obtener el flujo reactivo de tareas. Al sobreescribir el operador invoke, permite llamar al caso de uso como si fuera una función directamente. 

class GetTasksUseCase(private val repository: AcademicTaskRepository) {
    operator fun invoke(): Flow<List<AcademicTask>> {
        return repository.getTasksStream()
    }
}

4.2.4 Caso de Uso AddTaskUseCase (con Desafío Extra)

Contiene lógica de negocio pura: valida que el título no esté vacío y que cumpla el mínimo de 5 caracteres antes de invocar la infraestructura. Esta validación vive en el dominio porque es una regla del negocio, no de la UI. 

class AddTaskUseCase(private val repository: AcademicTaskRepository) {
    suspend operator fun invoke(title: String) {
        if (title.trim().isBlank()) {
            throw IllegalArgumentException("El título no puede estar vacío.")
        }
        if (title.trim().length < 5) {
            throw IllegalArgumentException(
                "La regla de dominio exige un mínimo de 5 caracteres."
            )
        }
        repository.addTask(title.trim())
    }
}

4.3 Capa de Datos (Data Layer)

La capa de datos provee la implementación concreta del contrato definido en el dominio. InMemoryTaskRepository simula una base de datos reactiva usando MutableStateFlow, que emite una nueva lista cada vez que se modifica su valor, propagando automáticamente los cambios a todos los colectores suscritos. 

class InMemoryTaskRepository : AcademicTaskRepository {

    private val tasksFlow = MutableStateFlow<List<AcademicTask>>(
        listOf(
            AcademicTask(UUID.randomUUID().toString(), "Estudiar Patrón MVVM", false),
            AcademicTask(UUID.randomUUID().toString(), "Analizar principios de Clean Architecture", true)
        )
    )

    override fun getTasksStream(): Flow<List<AcademicTask>> = tasksFlow

    override suspend fun addTask(title: String) {
        val newTask = AcademicTask(UUID.randomUUID().toString(), title, false)
        tasksFlow.value = tasksFlow.value + newTask
    }

    override suspend fun toggleTaskCompletion(taskId: String) {
        tasksFlow.value = tasksFlow.value.map { task ->
            if (task.id == taskId) task.copy(isCompleted = !task.isCompleted) else task
        }
    }
}
Nota: MutableStateFlow actúa como una base de datos en memoria reactiva. Cada asignación a .value dispara automáticamente la emisión de la nueva lista a todos los colectores suscritos, sin necesidad de notificación manual.

4.4 Capa de Presentación (Presentation Layer — MVVM + UDF)

4.4.1 Estados de la UI (Sealed Class)

Se utiliza una sealed class para modelar los estados lógicos finitos de la interfaz. Esto garantiza que el when en Compose sea exhaustivo y que ningún estado quede sin tratamiento en la vista. 

sealed class AcademicTaskUiState {
    object Loading : AcademicTaskUiState()
    data class Success(val tasks: List<AcademicTask>) : AcademicTaskUiState()
    data class Error(val message: String) : AcademicTaskUiState()
}

enum class ScreenType { LIST, CREATE }

4.4.2 AcademicTaskViewModel

El ViewModel cumple cuatro responsabilidades clave bajo el patrón UDF:

  • Mantiene el estado interno como MutableStateFlow (privado e inaccesible).
  • Expone únicamente el StateFlow inmutable de solo lectura hacia la vista.
  • Coordina los Use Cases mediante viewModelScope (coroutine lifecycle-aware).
  • Gestiona la navegación entre pantallas con mutableStateOf de Compose Runtime.
class AcademicTaskViewModel(
    private val getTasksUseCase: GetTasksUseCase,
    private val addTaskUseCase: AddTaskUseCase,
    private val repository: AcademicTaskRepository
) : ViewModel() {

    private val _uiState = MutableStateFlow<AcademicTaskUiState>(AcademicTaskUiState.Loading)
    val uiState: StateFlow<AcademicTaskUiState> = _uiState.asStateFlow()

    var currentScreen by mutableStateOf(ScreenType.LIST)
        private set

    init { observeTasks() }

    private fun observeTasks() {
        viewModelScope.launch {
            getTasksUseCase().collect { taskList ->
                _uiState.value = AcademicTaskUiState.Success(taskList)
            }
        }
    }
    // ... onTaskCheckedChange(), onSaveTask(), onNavigateToCreate(), etc.
}

4.4.3 Vistas Declarativas (AcademicTaskScreen.kt)

Las vistas Compose son componentes puramente declarativos: no almacenan ni gestionan datos, solo reaccionan a las emisiones del estado inmutable mediante collectAsState(). La función AcademicTaskApp actúa como enrutador entre las dos pantallas.

4.5 Orquestación en MainActivity

La MainActivity actúa como punto de entrada y compositor del grafo de dependencias, manteniendo la separación de responsabilidades: no contiene lógica de negocio ni accede directamente a datos. 

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()

        val repository = InMemoryTaskRepository()
        val getTasksUseCase = GetTasksUseCase(repository)
        val addTaskUseCase = AddTaskUseCase(repository)
        val viewModel = AcademicTaskViewModel(getTasksUseCase, addTaskUseCase, repository)

        setContent {
            ProgramacionMovilTheme {
                AcademicTaskApp(viewModel = viewModel)
            }
        }
    }
}

6. Desafío Extra — Regla de Dominio: Mínimo 5 Caracteres

Enunciado: Implementar una regla de negocio en la capa de Dominio que prohíba estrictamente ingresar tareas cuyo título tenga menos de 5 caracteres, gatillando un estado de error controlado y recuperable desde la UI sin crashes.

6.1 Implementación en el Dominio

La validación se implementó directamente en AddTaskUseCase, que es el lugar correcto según Clean Architecture: la regla pertenece al dominio y no debe vivir en la UI ni en el repositorio. 

// AddTaskUseCase.kt
if (title.trim().length < 5) {
    throw IllegalArgumentException(
        "La regla de dominio exige un mínimo de 5 caracteres."
    )
}

Cuando el ViewModel invoca addTaskUseCase(newTaskTitle) y el título no supera los 5 caracteres, la excepción es capturada por el bloque catch (e: IllegalArgumentException) del ViewModel, que emite AcademicTaskUiState.Error(e.message) sin propagar el crash a la Activity.

6.2 Recuperación Controlada en la UI

Se actualizó el bloque del estado Error en AcademicTaskListScreen para incluir un botón "Reintentar" que navega de vuelta al formulario, permitiendo al usuario corregir el título sin necesidad de reiniciar la aplicación. 

is AcademicTaskUiState.Error -> {
    Column(horizontalAlignment = Alignment.CenterHorizontally) {
        Text(
            text = state.message,
            color = MaterialTheme.colorScheme.error,
            style = MaterialTheme.typography.bodyLarge
        )
        Spacer(modifier = Modifier.height(10.dp))
        Button(onClick = { viewModel.onNavigateToCreate() }) {
            Text("Reintentar")
        }
    }
}

8. Conclusiones

  1. La separación física de capas elimina el antipatrón "God Activity". Al dividir el código en paquetes domain, data y ui, cada componente tiene una única responsabilidad bien definida. El resultado es un código significativamente más legible, mantenible y resistente a cambios en cualquier capa sin afectar a las demás.
  2. El Flujo Unidireccional de Datos (UDF) con StateFlow garantiza coherencia del estado. Al exponer únicamente un StateFlow inmutable desde el ViewModel, se elimina la posibilidad de que la vista modifique el estado directamente, lo que previene condiciones de carrera e inconsistencias visuales. Cada cambio de estado es trazable y predecible.
  3. Los Use Cases hacen la lógica de negocio portátil y testable. Al encapsular cada operación en un caso de uso independiente del framework de Android, es posible probar la lógica de validación (por ejemplo, el mínimo de 5 caracteres del Desafío Extra) con pruebas unitarias puras en JVM, sin necesidad de emulador ni mocks complejos.
  4. MutableStateFlow como repositorio en memoria es una solución efectiva para prototipos. Emitir flujos reactivos desde un MutableStateFlow permite simular el comportamiento de una base de datos real (Room) con una fracción de la complejidad, siendo ideal para demostrar patrones arquitectónicos sin distractores de infraestructura.
  5. El manejo de errores en el ViewModel evita crashes sin sacrificar la experiencia de usuario. Capturar las IllegalArgumentException del dominio dentro del viewModelScope y emitirlas como AcademicTaskUiState.Error permite mostrar mensajes descriptivos y opciones de recuperación, cumpliendo con los estándares de robustez de aplicaciones de producción.

9. Recomendaciones

  1. Adoptar Hilt o Koin para la inyección de dependencias. En este laboratorio la orquestación se realizó manualmente en MainActivity. En proyectos de producción se recomienda usar un framework de DI como Hilt (oficial de Google) para eliminar el boilerplate, gestionar el ciclo de vida de los objetos y facilitar el reemplazo de implementaciones en pruebas.
  2. Implementar Room para persistencia real de datos. El repositorio en memoria pierde todos los datos al cerrar la aplicación. Se recomienda migrar InMemoryTaskRepository a una implementación con Room Database, manteniendo intacto el contrato AcademicTaskRepository, lo cual no requiere modificar ninguna otra capa (demostración del principio Open/Closed de SOLID).
  3. Agregar un ToggleTaskCompletionUseCase para completar el patrón. La operación de alternar el estado de completado actualmente llama directamente al repositorio desde el ViewModel. Para mantener la coherencia arquitectónica, se recomienda crear un ToggleTaskCompletionUseCase que encapsule esta operación y permita agregar reglas de negocio futuras (por ejemplo, auditoría de cambios).
  4. Agregar el uso de ViewModelFactory para sobrevivir rotaciones correctamente. En la implementación actual, el ViewModel se instancia manualmente en onCreate, lo que significa que no está gestionado por el ViewModelStore. Para proyectos reales se debe usar ViewModelProvider.Factory o viewModels() con Hilt, garantizando que el ViewModel y su estado sobrevivan completamente a los cambios de configuración.
  5. Implementar pruebas unitarias para los Use Cases. Al ser independientes del framework, GetTasksUseCase y AddTaskUseCase pueden probarse con JUnit 4/5 usando un repositorio falso (fake). Se recomienda implementar al menos un test que verifique que el AddTaskUseCase lanza IllegalArgumentException ante títulos de menos de 5 caracteres.
